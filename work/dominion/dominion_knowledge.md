# ドミニオン実装ナレッジ・リスク管理表

本ドキュメントは、ドミニオンの実装過程で得られた知見、設計上の課題、および将来のカード拡張に伴う潜在的リスクをまとめたものです。

---

## 1. プロンプト処理と非同期チェーン（連鎖）の管理

### 1.1 概要（プロンプト処理）

カードの効果の中には、プレイヤーにカードの選択や獲得を促す「プロンプト（`ActionPrompt`）」を生成するものがあります。
通常のプレイ処理フローは同期的ですが、プロンプトが発行されると入力待ち状態（非同期）となります。

### 1.2 発見された課題（玉座の間バグ）

「玉座の間（指定したアクションカードを2回プレイする）」のようなメタカードにおいて、子カードがプロンプトを発行する場合に問題が発生しました。
元の実装では、1回目のプレイ直後にプロンプトが発行されたかどうかにかかわらず、即座に2回目のプレイを実行してしまっていました。その結果、1回目のプロンプトが2回目のプロンプトで上書きされたり、内部状態が矛盾するバグが発生しました。

### 1.3 解決策と実装指針（hookPrompt / executingCount）

1. **プロンプト解決のフック（`hookPrompt`）**
   プロンプトが発行された場合、そのプロンプトの `onConfirm` コールバックをフックし、解決（`clearPrompt`）を待ってから次の一連の処理を手動で再開する仕組みを導入しました。
2. **実行中フラグ（`executingCount`）によるフェーズ移行ガード**
   `玉座の間` のように、「プロンプトを一旦解除して、その後にさらにアクションが続く」場合のフェーズ移行バグを解決するため、プレイヤー状態に `executingCount` カウンターを導入しました。これにより、一連のアクションシーケンスが完全に終わるまで、自動的な購入フェーズ移行（`checkActionPhase`）を一時停止できるようになりました。

### 1.4 ⚠️ 将来拡張時のリスク（メタカード）

- **宮廷 (King's Court)**：3回プレイするカードでも同様の管理が必要です。
- **行進 (Procession)** などの複雑なメタカードや、**家臣 (Vassal)** のような「通常と異なるタイミングでカードをプレイ・処理する」カードを追加する際は、必ずプロンプトクリアのタイミングと効果の連鎖順序をテストする必要があります。
- 複数のメタカードがネストする場合（玉座の間で玉座の間をプレイするなど）に備え、フラグは `boolean` ではなく `number`（カウンター）として管理し、全ての処理が完了したときのみフェーズ移行を許容するようにすべきです。

## 2. フェーズ進行制御（自動移行とガード）

### 2.1 概要（自動移行ガード）

ドミニオンには、「アクション権がなくなり、かつアクションカードも持っていない」場合に自動的に購入フェーズへ移行する利便性向上のためのロジック（`checkActionPhase`）を組み込んでいます。

### 2.2 発見された課題（メタカードによる強制移行）

メタカード（`玉座の間` 等）が自身のプロンプトを解決（`clearPrompt`）した際、その時点でのアクション数が 0 であると、後続のプレイでアクションが追加される予定であっても、システムが「フェーズ終了」と誤判定して購入フェーズへ強制移行してしまう問題が発生しました。

### 2.3 解決策と実装指針（executingCount / helpers拡張）

- `helpers.checkActionPhase()` を `ActionHelpers` に追加し、カード側から必要に応じて明示的にフェーズ判定をリクエストできるようにしました。
- `executingCount > 0` の間は `checkActionPhase` がフェーズを終了させないようガードを設けました。
- 非同期（プロンプトを伴う）連鎖がある場合は、最後の連鎖が終わったあとに `checkActionPhase` を呼び、そこで初めて正常なフェーズ判定が行われるようにしました。

### 2.4 アクティブターンとインタラクションの分離

UI上で「購入フェーズへ」や「ターン終了」のボタンを押せる状態（`canProgressPhase`）は、プロンプトへの応答操作（`canInteract`）とは厳密に分離されています。相手のターン中にアタックへのリアクションなどで操作が可能（`canInteract = true`）であっても、フェーズ進行ボタンは自身のターンでない限り無効化される設計となっています。

### 2.5 ⚠️ 将来拡張時のリスク（フェーズ制御）

- 相手のターン中に処理や選択が挟まる**リアクションカード**や獲得が発生した場合、メインのフェーズ進行UIが誤操作されないよう、UIの状態定義には常に注意が必要です。

## 3. サプライ獲得条件（プロンプト制約）の柔軟性

### 3.1 概要（サプライ獲得制約）

「工房（コスト4まで）」「鉱山（コスト+3の財宝）」など、サプライから特定の条件に合致するカードのみを獲得させる効果が存在します。

### 3.2 発見された課題（獲得制約の無視）

UIのハイライト表示（`is-gainable`）が、プロンプトごとの固有の制約（コスト上限やカードタイプ）を知らなかったため、獲得不可能なカードまでハイライトされ、クリック判定が通ってしまう問題がありました。

### 3.3 解決策と実装指針（ActionPromptの拡張）

`ActionPrompt` インターフェースを拡張し、`allowedCost`（最大コスト）と `allowedTypes`（必須カードタイプ）などのプロパティを持たせました。UI側はこれを読み取り、条件に合致しないサプライのカードをクリック不可・暗転（`unpurchasable`）させるように修正しました。

### 3.4 ⚠️ 将来拡張時のリスク（獲得制約）

- 「コストが全く同じカード（鉄工所など）」
- 「特定のカードタイプを持たないカード」
- 条件が複雑な獲得（「アクションカードなら〜、財宝カードなら〜」と分岐するもの）
、今後の拡張セット実装時に、`allowedCost` 等の単純なパラメータ制限だけでは表現しきれない「獲得条件」が出てくる可能性があります。その場合は `allowedCost` 等の代わりに `isSelectable?: (card: Card) => boolean` といった関数評価をプロンプトに渡すような、より柔軟なフィルタリング機構へのリファクタリングを検討すべきです。
